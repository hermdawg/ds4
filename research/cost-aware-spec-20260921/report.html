What was possible on this machine

The installed model is DeepSeek V4 Flash 0731 IQ2XXS/w2Q2K, with 80.76 GiB of weights. It cannot stay fully resident in 64 GiB of memory. Its matching DSpark support file was absent, and no supported Qwen or GLM GGUF with built-in drafting was found. No checkpoints were downloaded.

DSpark is a small helper that proposes future tokens; the main model checks them before committing output. Without that helper, this campaign could measure ordinary decoding and isolated GPU operations, but could not test speculative model output, recovery or speed. The authorized fallback was used. The work is isolated on your research branch; production source files are unchanged.

The local checkout was frozen rather than mixing the experiment with 62 newer upstream commits. Main checkout and existing user files were preserved. The campaign began at 20:44:55 UTC and stopped early after completing the fallback study. Further model-level optimization requires the missing matched drafter; more invented-cost trials cannot resolve that blocker.

What the existing scheduler already does

The current DSpark scheduler checks accepted-draft counts over short windows, pauses unproductive drafting, retries later, uses confidence to skip proposals, and avoids the output tail. It also has optional elapsed-cost gates, disabled by default to keep the schedule reproducible. Qwen has a different acceptance-based policy for one or two drafts.

Two details matter for cost accounting: resident M5 seed batching starts at three proposals, and a smaller verification cap can be applied after much of the draft work has happened. A seed is useful output, but it is not a successful draft. The existing optional cost gate is not a direct full-cycle cost-per-token comparison and may use an old ordinary-token cost.

The candidates learn a ratio of elapsed cycle time to committed tokens, including draft, verification and recovery. They also sample ordinary decode and occasionally retry other caps. H1 tries caps 0–5. H2 tries only 0, 3 and 5. Both were calibrated on the tuning split and frozen before evaluation.

Instrumentation can change what it measures

Host bookkeeping

In the isolated C build, policy selection plus two monotonic timer reads took about 38 ns/cycle, comparable to two timer reads alone. This does not include GPU synchronization or inference integration.

Real SSD timing counters

Eight ordinary-model runs in ABBA/BAAB order produced identical greedy text. The existing timing summary changed paired elapsed time by a median 2.2%, with pair ratios 1.002, 1.042, 0.971, 1.048. The spread makes this a rough overhead estimate. Timed runs are diagnostic, not the headline baseline.

GPU completion boundaries

For three isolated Q8 projections, adding a wait after each stage changed median elapsed time from 0.192 to 0.491 ms at width 1024/one row, and from 0.461 to 0.772 ms at width 4096/six rows. All timing variants matched exactly and passed an independent dot-product reference.

Measure complete cycles at existing synchronization points. Host enqueue timestamps measure submission, not completed GPU work. If stage detail needs extra waits, measure it separately and quantify its overhead.

The projection benchmark is not a transformer, draft model or verifier. Existing SSD counters overlap in time and cannot be added to reconstruct full generation time. New speculative-stage instrumentation overhead remains unverified.

Why the break-even point changes

Let t be the cost of one ordinary target token, D draft cost, V verification cost, R expected recovery cost, and A expected accepted drafts. A cycle commits one seed plus A drafts. Its cost per token is total cycle cost divided by 1 + A.

Separate seed: (t + D + P(verify)V + R)/(1 + A) < t
⇒ D + P(verify)V + R < tA

Batched seed, all proposals verified: (D + V + R)/(1 + A) < t
⇒ D + V + R < t(1 + A)

For example, if t = 20 ms and draft + verification + recovery = 32 ms, a separate-seed cycle that always verifies needs more than 1.6 accepted drafts. If the same 32 ms cycle already includes the seed, it needs more than 0.6. Those numbers illustrate the accounting; they are not measured model costs.

Acceptance and estimator derivation

If each proposed token independently matches with probability p, draft position i survives only if all i preceding decisions succeed, with probability pi. Summing survival probabilities gives the expected accepted prefix:

A = p + p² + … + pᵈ = p(1 − pᵈ)/(1 − p), for p ≠ 1.
A = d when p = 1.

The simulator allows different first/later probabilities and confidence-pruned proposals. The C policy does not assume independent acceptance: it observes actual committed counts supplied by its caller. For an action, it updates time sum S and token sum N as follows:

S ← 0.95 S + elapsed_ms
N ← 0.95 N + committed_tokens
estimated cost per token = S/N

A ratio of totals weights each token correctly. Averaging per-cycle ratios would give a one-token rejection and a six-token acceptance the same weight. The 0.95 decay retains roughly 20 observations per action; rarely tried actions can therefore hold stale evidence for many output tokens. Exploration helps recovery but also has a cost.

Correctness and the retained patch

No production implementation was changed. The retained patch lives under research/cost-aware-spec-20260921/: a small backend-independent policy, source-backed control bridge, frozen inputs, bounded runners, tests, raw data and this report.

  • Passed the existing sampling distribution checks, CPU/GPU session-state tests, speculative rollback test, Qwen kernels, MoE reference comparisons, SSD expert eviction, GLM recurrent kernels, Q8 projection tests, Metal kernel group and server unit group.
  • Passed policy sanitizer tests for invalid timings, weighted ratios, legal depths, output limits, context buckets, reset and recovery. Analytical simulator checks and replay of frozen H1 outcomes also passed.
  • Fixed a nested-timeout cleanup trap in the research runner; tests verify child processes stop. Final analysis refuses incomplete model results.
  • Still unverified: speculative model correctness, rejection/cache/recurrent-state integration, real exact-sampling behavior under the new policy, session reuse with policy-driven execution, and any CUDA performance claim. Unit tests cannot replace these checks.

What should transfer to NVIDIA serving

The useful idea is the accounting: include all elapsed work, compare against ordinary decoding, count committed tokens, respect output limits, and retain occasional exploration. Re-measure draft/verification/recovery costs, context effects and legal caps on the intended hardware. CUDA graph size boundaries and expert activation can make cost curves uneven.

Concurrent requests change the objective. A draft that speeds up one request may consume verification capacity needed by others. Optimize useful aggregate throughput in tok/s/GPU while checking TPS and latency. This local single-request campaign establishes no production-serving gain.

There is relevant prior art: vLLM's DSpark adaptive verification already uses separate profiled cost tables and confidence survival to choose a global verification budget. EVICT studies verification costs from activating more experts. These sources motivate a batch-aware follow-up; their performance figures are not part of this report.

Most promising next experiment: use a resident matched target/drafter pair, first measure ordinary and fixed caps 3 and 5, then test cost plus existing confidence signals in interleaved runs. Include concurrent-request batches before considering a serving change. No new drafter training or broad CUDA port is justified by these results.
